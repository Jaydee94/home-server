# k3s

k3s ist die Single-Node-Kubernetes-Distribution des Home-Servers. Die Ansible-Rolle installiert k3s und Helm, schreibt die Server-Konfiguration und richtet den kubeconfig für den Login-User ein.

| | |
|---|---|
| Rolle | [`ansible/roles/k3s/`](../ansible/roles/k3s/) |
| Make | `make k3s` |
| Konfiguration | `/etc/rancher/k3s/config.yaml` (aus [`k3s-config.yaml.j2`](../ansible/roles/k3s/templates/k3s-config.yaml.j2)) |
| Kubeconfig | `/etc/rancher/k3s/k3s.yaml` (root, `0600`), Kopie in `~/.kube/config` des `ansible_user` |
| Daten | `/var/lib/rancher/k3s/` |

## Konfiguration

Versionen und Netze stehen in [`ansible/group_vars/all.yml`](../ansible/group_vars/all.yml), die kubelet-Reserven in [`ansible/roles/k3s/defaults/main.yml`](../ansible/roles/k3s/defaults/main.yml).

| Variable | Wert | Zweck |
|---|---|---|
| `k3s_version` | `v1.37.2+k3s1` | Gepinnte k3s-Version. Leer heißt: bei jedem Lauf `k3s_channel` folgen. |
| `k3s_channel` | `stable` | Nur wirksam, wenn `k3s_version` leer ist |
| `k3s_pod_cidr` | `10.42.0.0/16` | Pod-Netz (Flannel VXLAN) |
| `k3s_service_cidr` | `10.43.0.0/16` | Service-ClusterIPs, CoreDNS auf `10.43.0.10` |
| `helm_version` | `v3.22.1` | Gepinnte Helm-Version, nur Helm 3 (Installer `get-helm-3`) |
| `k3s_kubelet_system_reserved` | `cpu=250m,memory=1Gi` | Reserve für Host-Dienste außerhalb von Kubernetes |
| `k3s_kubelet_eviction_hard` | `memory.available<500Mi,nodefs.available<10%,imagefs.available<5%` | Ersetzt die k3s-Defaults komplett, deshalb steht `imagefs` mit drin |
| `k3s_kubelet_image_gc_high_threshold` / `_low_threshold` | `75` / `65` | Image-GC startet bei 75 % Plattenbelegung und räumt bis 65 % |

Die Rolle startet den Installer nur, wenn k3s fehlt oder die installierte Version von `k3s_version` abweicht. Ändert sich `config.yaml`, startet der Handler `Restart k3s` den Dienst einmal neu. Die API ist dann kurz weg, die Container laufen weiter (`KillMode=process`).

k3s bringt Traefik v3 (Ports 80/443 über Klipper-ServiceLB), CoreDNS, Flannel und den `local-path`-Provisioner mit. `local-path` legt Volumes unter `/var/lib/rancher/k3s/storage/` ab, nur `ReadWriteOnce`, ohne Quota und mit ReclaimPolicy `Delete`. Wie PVCs trotzdem vor ArgoCD-Prunes geschützt sind, steht in [Gotchas: ArgoCD / GitOps](gotchas.md#argocd--gitops). Für LAN-IPs einzelner Services läuft zusätzlich MetalLB neben Klipper ([Gotchas: MetalLB](gotchas.md#metallb--networking)).

## Upgrades

Renovate öffnet für neue k3s- und Helm-Releases einen PR auf `ansible/group_vars/all.yml` (Annotation `# renovate:` über der Variable). Diese PRs werden nie automatisch gemergt, Helm-Major-Updates sind abgeschaltet ([`renovate.json`](../renovate.json)). Nach dem Merge rollt der tägliche Semaphore-Lauf um 06:00 das Upgrade aus, sofort geht es mit `make k3s`.

Vor einem Minor-Sprung die [k3s-Release-Notes](https://github.com/k3s-io/k3s/releases) auf entfernte APIs und geänderte Bundle-Komponenten prüfen.

## Betrieb

```bash
# Dienst und Logs
sudo systemctl status k3s
sudo journalctl -u k3s --since "10 minutes ago"

# Wirksame kubelet-Werte und Allocatable prüfen
sudo kubectl get --raw /api/v1/nodes/homeserver/proxy/configz \
  | jq '.kubeletconfig | {systemReserved, evictionHard, imageGCHighThresholdPercent, imageGCLowThresholdPercent}'
sudo kubectl describe node homeserver | grep -A8 Allocatable
```

`config.yaml` nicht von Hand ändern: Ansible überschreibt die Datei beim nächsten Lauf. Werte über die Variablen oben setzen und `make k3s` ausführen.

## Backup

Datastore (SQLite unter `/var/lib/rancher/k3s/server/`), Sealed-Secrets-Keys und Volumes sichert das nächtliche Backup, siehe [Backup](26-backup.md). Alle Workloads kommen aus Git zurück (Playbook plus ArgoCD-Sync), die Volume-Daten und die Sealed-Secrets-Keys nicht.

> [!WARNING]
> Ohne Backup der Sealed-Secrets-Keys lassen sich die SealedSecrets im Repo nach einer Neuinstallation nicht mehr entschlüsseln.
